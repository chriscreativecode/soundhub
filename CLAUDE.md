# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev            # Serve examples/ with the library aliased to src/
npm run build          # Typecheck, then build dist/ and dist/types/
npm run typecheck      # tsc --noEmit
npm test               # Vitest, once
npm run test:watch     # Vitest, while you work
npm run test:coverage  # Vitest with a coverage report
```

Tests live in `tests/`, with the Web Audio mock and helpers in `tests/support`.
They run against `src/`, not `dist/`. A bug fix gets a test that fails without
it; new public API gets tests in the file for its area.

## Architecture

The library lives in `src/core/`, exported through `src/index.ts`. The demo suite
is a separate repository (soundhub-showcase); `examples/` here holds one page
that exercises the whole public API and doubles as a compile-time smoke test.

Buffered sounds are decoded into an AudioBuffer. Streams (`loadStream`) are
backed by an HTMLAudioElement instead, and every stream operation is an early
return at the top of the matching public method, guarded on the `streams` map.
Keep it that way: the buffered path should stay untouched by stream work.

Audio in `examples/sounds/` is generated by `scripts/generate-example-sounds.py`,
so the folder carries the same MIT licence as the code. Do not add sampled or
downloaded audio there.

## What else reads this repository

Two sibling repositories build on this one and both read it directly, so a
change here can show up there without anyone publishing anything.

- `soundhub-showcase` is the demo site. Its `node_modules/soundhub` is a link to
  this folder, and `npm run dev` there resolves `soundhub` to `src/index.ts`
  here. A production build of the showcase bundles whatever is in `dist/`, so
  build this project before building that one.
- `soundhub-docs` generates one page per method from `SoundHubInterface`. That
  makes the interface the published contract twice over: it is what the docs
  describe and what the generator can see. A public method that is missing from
  it gets no page and no maintenance.

## Releasing

The version sits in `package.json` and in `VERSION` in `sound-hub.ts`, and a
test fails when those two disagree. The changelog needs its heading dated and
the link at the bottom pointing at the new tag. `prepublishOnly` runs the tests
and the build, so `npm publish` cannot ship a stale `dist/`.

Old names stay until the next major version. `SoundManager`,
`SoundManagerConfig` and `createNewInstance` are all still exported or honoured,
marked deprecated, and go in v7.

## Writing style

Anything a person will read carries my name, so it should read as if I wrote it.
That covers the README, the changelog, release notes, documentation pages, code
comments, commit messages and UI copy.

- No em dashes or en dashes in prose. Use a full stop, a comma, a colon or
  parentheses instead. Number ranges get the word "to".
- Plain, short sentences. Say what a thing does before saying why it matters.
- Skip the rhetorical scaffolding: no "this is not just X, it is Y", no forced
  groups of three, no participle clauses tacked on to add weight, no promotional
  adjectives.
- Vary sentence length rather than making every line land like a closing
  statement.

Run the humanizer skill over any longer piece of prose before handing it over,
and check for dashes before calling it done. For README.md this is not optional:
every rewrite of it goes through the humanizer skill first, because that file
ships to npm and is the first thing anyone reads.
