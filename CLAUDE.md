## Architecture

**sound-manager-ts** is a Web Audio API library, distributed as an npm package. The build produces ES module and UMD outputs alongside `.d.ts` declarations (via vite-plugin-dts).

### Core library (`src/sound-manager/`)

The entire public surface is one class: **`SoundManager`** (`sound-manager.ts`), which implements `SoundManagerInterface` — that interface is the source of truth for what is exposed. `src/index.ts` re-exports everything that forms the public API.

### Audio pipeline

Each loaded sound goes through this node graph (assembled by `AudioNodeConnector`):

```
Source (AudioBufferSourceNode / HTMLAudioElement)
  → GainNode (per-sound volume)
  → StereoPannerNode  OR  PannerNode (depends on pan type)
  → GainNode (master volume)
  → AudioContext.destination
```

Panning type is set per-sound and can switch between stereo (`StereoPannerNode`) and spatial (`PannerNode` with HRTF or EqualPower). Spatial position is tracked via a `ConstantSourceNode`.

### Instance model

A single registered sound can be played as multiple simultaneous instances (`createNewInstance`). `SoundManager` tracks all live instances internally; each has its own node graph and state (playing / paused / stopped).

### Demo (`src/demo/`)

The demo is self-contained and not part of the library output.

### Readme (`src/readme/`)

The docs site is a static HTML page generated by injecting the README.md (processed with markdown-it + highlight.js) into `template.html`. Run `npm run build:docs` to regenerate after editing the README.

## Mandatory git workflow

At the end of every completed task, immediately create a git commit for that task.

Mandatory rules:
- A finished task must be committed right away
- Each commit should match exactly one completed task when possible
- A commit may include multiple files if they are all part of the same task
- Use a short, specific, descriptive commit message
- Do not delay commits until multiple tasks have accumulated
- Do not retroactively split tasks into separate commits after later work has already been added
- Never reset, revert, rewrite, or roll back newer work to create an earlier missing commit
- If a clean commit per task is no longer possible, explain why and ask the user before doing anything with git history

Before creating a commit:
- Run `git status`
- Review all modified files
- Include all changes that are necessary for the completed task
- Do not include unrelated or accidental changes in the same commit
- If both task-related and unrelated changes are present, stop and ask for clarification first
- If the changed files cannot be safely separated, ask the user before proceeding

Commit message guidance:
- Use clear commit messages that match the completed task
- Prefer formats like:
  - `feat: add feature A`
  - `fix: resolve scoring bug in pong collision logic`
  - `refactor: simplify game loop update flow`
  - `docs: update README usage instructions`

Safety rules:
- Never perform `git reset --hard` unless the user explicitly asks for it
- Never force push unless the user explicitly asks for it
- Never rebase unless the user explicitly asks for it
- Never rewrite commit history unless the user explicitly asks for it
- Never revert remote commits to recover a missed local commit boundary
- If a missed commit boundary cannot be recovered safely, do not attempt to fix it with git history operations
- Ask the user what to do next instead of taking destructive git actions
